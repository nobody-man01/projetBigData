# Décisions techniques (une ligne par décision : décision, alternatives, raison)

| Date | Décision | Alternatives écartées | Raison |
|---|---|---|---|
| 2026-10-06 | Données : PaySim pour entraîner/valider + générateur v1 pour la démo, même format via adaptateur | Générateur seul ; PaySim seul ; données réelles | Aucune donnée réelle publique ; PaySim est une référence citée (crédibilité) ; le générateur apporte le contexte camerounais et la démo en direct |
| 2026-10-06 | Générateur v1 : comptes persistants, XAF entiers, 3 scénarios de fraude dont un très difficile (SCAM), cas normaux trompeurs | Tirages indépendants par transaction (v0) | La v0 donnait des fraudes triviales (100 % de soldes vidés) et des montants irréalistes (centimes) : des métriques gonflées n'auraient aucune valeur |
| 2026-10-06 | `add_features` : l'erreur de solde du destinataire tient compte du CASH_IN (l'agent donne du e-money) | Formule unique pour tous les types | Sinon un signal faux est créé pour tous les dépôts |
| 2026-10-14 | Features d'historique par compte (appareils, destinataires, villes, montant moyen) calculées en batch puis jointes au flux (jointure flux / table statique) | Agrégats en fenêtres glissantes dans le streaming ; features de la seule transaction | Les trois scénarios de fraude se définissent par rapport aux habitudes du compte : AUC-PR 0,39 → 0,80 sur la période de test. Architecture de type Lambda (couche batch + couche temps réel), simple et sans état dans le streaming |
| 2026-10-14 | Découpage temporel en 3 tranches : profils 0-50 %, entraînement 50-80 %, test 80-100 % (profils recalculés sur 0-80 %) | Découpage aléatoire ; profils calculés sur tout le jeu | Évite toute fuite du futur vers le passé ; reproduit la situation de production |
| 2026-10-14 | Gradient boosting (GBT) retenu | Régression logistique (AUC-PR validation 0,60), forêt aléatoire (0,72) | Meilleure AUC-PR sur la tranche de validation 70-80 % (0,82), choisie sans regarder le test |
| 2026-10-14 | Latence mesurée par un horodatage `sent_at` ajouté par le producer | Estimation théorique | Chiffre réel pour le rapport ; le micro-lot de 5 s de Spark domine la latence (médiane ≈ 5,6 s) |
| 2026-10-17 | Données v2 (générateur de M2) et test sur une période postérieure séparée de 7 jours à 0,3 % de fraudes | Test sur la fin du même mois à 2 % | Plus proche de la réalité ; évite qu'un taux de fraude élevé n'embellisse la précision |
| 2026-10-18 | Features de fréquence (opérations sur 10 min et 1 h, répétitions vers le même destinataire) calculées par la même fonction de fenêtres à l'entraînement et en temps réel (historique d'1 h gardé entre les micro-lots) | État Spark dédié (applyInPandasWithState) ; calcul dans le producer | Une seule définition, testée (égalité batch / micro-lots) ; corrige le fractionnement par agent (0 % → 89 % détectés au seuil critique) |
| 2026-10-18 | Forêt aléatoire retenue (remplace le GBT du 14/10) | GBT (AUC-PR validation 0,887), régression logistique (0,774) | Meilleure AUC-PR de validation (0,893) ; sur le test : AUC-PR 0,80, contre 0,41 sans fréquence, 0,61 sans profils et 0,06 sans les deux |
| 2026-10-18 | Mode cluster Docker : Kafka 3 brokers (3 partitions, réplication 3, min.insync.replicas=2) et Spark standalone (1 master, 2 workers), le mode simple restant disponible | Cluster sur machines virtuelles ; Kubernetes | Montre la répartition et la tolérance aux pannes sur une seule machine ; test : un broker arrêté 60 s pendant le flux, 3 000 transactions envoyées, 3 000 scorées, 0 doublon |
| 2026-10-18 | PaySim complet (6,36 M transactions) entraîné avec le même code, en local et sur le cluster ; jointure répartie des profils au-delà de 500 000 comptes | Échantillon de PaySim ; copie (broadcast) systématique des profils | Démontre le passage à l'échelle ; le broadcast échoue avec 5,09 M de comptes dans la table des profils de test (mémoire du driver). AUC-PR 0,9996, à relativiser : 99,85 % des comptes n'ont qu'une transaction et la comptabilité des soldes sépare presque seule les fraudes dans ce simulateur |
| 2026-10-18 | Conclusion sur le cluster : pas d'accélération sur une seule machine (224 s contre 258 s sur nos données, 893 s contre 653 s sur PaySim, à mémoire locale égale) | Présenter le cluster comme plus rapide | Mesures honnêtes ; l'intérêt démontré est la tolérance aux pannes et l'extensibilité |
| 2026-10-18 | Page « Investigation d'un compte » : habitudes connues (profils de la couche batch) comparées aux transactions du flux, chronologie, comptes liés, décisions simulées avec confirmation ; chaque numéro de compte des alertes y mène | Simple tableau des comptes à risque | L'analyste voit en un écran pourquoi agir (appareil jamais vu, destinataire nouveau) et remonte la chaîne victime → mule ; aucune action réelle n'est envoyée |
| 2026-10-18 | Mode clair en plus du mode sombre (interrupteur dans la barre latérale, `?theme=clair` dans l'adresse), tableaux HTML du thème à la place de st.dataframe, graphiques Plotly sans le thème natif de Streamlit | Menu de réglages natif de Streamlit (masqué chez nous, et sans effet sur notre CSS) | Lisibilité au vidéoprojecteur et à l'impression ; st.dataframe et le thème Plotly de Streamlit ne suivent pas une palette changée en cours de session |
| 2026-10-18 | Curseur de seuil de la page Performance à crans : uniquement les seuils dont les chiffres sont exacts (points de la courbe PR enregistrée + 0,50 et 0,80) | Point de courbe le plus proche (121 fausses alertes affichées au lieu de 137 à 0,80) ; interpolation | Aucun chiffre approché affiché ; cohérence avec les cartes de la même page et avec le rapport |
